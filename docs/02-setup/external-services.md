# External Services

Status: 2026-08-06.

## Supabase contract persistence

SPEC-10 uses Supabase Postgres as the primary contract sink. Apply `supabase/migrations/20260724000000_contract_entries.sql`; it creates `contract_entries`, immutable `contract_submissions`, lifecycle `contract_events`, RLS, and the transactional `submit_contract_entry_role` function. All database access is server-side with `SUPABASE_SERVICE_ROLE_KEY`. Anonymous and authenticated browser roles receive no direct table or RPC privileges.

Raw role tokens are generated by the backend, returned only in newly created or regenerated URLs, and stored only as HMAC-SHA256 hashes. When the second role submits, the database transaction sets `status=complete` and stores `combined_submission`.

SPEC-11 stores tenant and guarantor DNI front/back pairs in a separate private Supabase Storage bucket. SPEC-17 makes both sides required for migrated entries, accepts JPG/PNG/WEBP/GIF/HEIC/HEIF images and PDF files, and rejects oversized objects, duplicate/extra slots, or paths outside the current entry. The server verifies the client role token before issuing a signed upload URL; the browser uploads directly and submits only the resulting private object reference. Apply `supabase/migrations/20260727000000_contract_spec11.sql` and `supabase/migrations/20260803000000_contract_spec17.sql` to provision and update the default `contract-dni` bucket.

SPEC-14 stores salary-receipt and property-guarantee evidence in the separate private `contract-evidence` bucket. Each guarantor may store at most two files in `recibo_sueldo_files` and two in `garantia_propietaria_files`, and must provide at least one file across those arrays. The exact allowlist is `application/pdf`, `image/jpeg`, `image/png`, `image/gif`, `image/webp`, `image/bmp`, and `image/tiff`; the default object limit is 10 MB. Apply `supabase/migrations/20260729000000_contract_spec14.sql` to provision the default bucket.

Evidence selection is passive. Only the explicit `Guardar` action requests signed upload URLs from the client-token-authorized, rate-limited evidence preflight endpoint, locks the editable form, uploads the selected files directly, and submits `{ filename, mimeType, size, storagePath, storageBucket }` references in the corresponding guarantor arrays. Successful uploads are retained as stable references for retry rather than uploaded twice.

Before persistence, the backend reads every referenced evidence object's private Storage metadata and requires the object to exist with the submitted MIME type and exact byte size. Missing, duplicated, mis-scoped, or mismatched references are rejected; temporary Storage verification failures return a retriable `503`.

Saved contract JSON contains bucket/path metadata, not a public URL or an expiring download URL. Both contract media buckets remain private. Administrator detail reads validate media references against the selected entry and configured bucket, then return ten-minute signed view URLs in the normalized inspection model. DNI media stays associated with its repeatable item; SPEC-14 evidence is grouped under its `Recibo de sueldo` or `Garantía propietaria` subsection. Bucket names and storage paths are not returned in the inspection model.

## Google Drive

The backend creates a property folder and uploads files to Google Drive.

- The parent folder ID is configured by `GOOGLE_DRIVE_PARENT_FOLDER_ID`.
- The backend supports User OAuth2 auth and a Service Account fallback.
- Drive uploads are subject to platform payload limits and Drive storage quotas.

## Google Sheets

The backend supports separate Sheet destinations for property and contract submissions.

- The target sheet ID is `GOOGLE_SHEET_ID`.
- The append range is `GOOGLE_SHEET_RANGE`.
- The row mapping is implemented in `backend/src/mappers/sheetRowMapper.ts`.

The retained SPEC-09 compatibility API uses a separate destination:

- `CONTRACT_GOOGLE_SHEET_ID` selects the spreadsheet.
- `CONTRACT_GOOGLE_SHEET_NAME` selects the tab.
- The authoritative contract schema determines deterministic field/column order.
- Before every append, the backend reads `'<sheetName>'!1:1` with `majorDimension=ROWS` and `valueRenderOption=FORMATTED_VALUE`.
- The complete returned header row must equal the configured headers by length and position. Duplicate labels are intentional and must occur in the same positions.
- Appends use `spreadsheets.values.append` with `valueInputOption=RAW`.
- Formula-like strings are escaped before append even though `RAW` is used.

Header preflight failure prevents the append. A missing, extra, or reordered header produces a non-retriable `500` mapping/configuration response that identifies the first mismatch and tells an administrator to update the configured tab before retrying.

Contract header reads and row appends authenticate only with `GOOGLE_SERVICE_ACCOUNT_KEY_JSON` through the dedicated service-account helper. Unlike the property workflow, they never select user OAuth credentials as a fallback.

`spreadsheets.values.append` has no application idempotency key in this implementation. The service retries transient provider failures, but a lost response can be ambiguous: Google may have committed the row even though the client received an error. Before any manual or UI retry after an ambiguous append failure, reconcile the destination Sheet using the time window and submitted values. The `retriable` flag classifies the upstream failure; it is not proof that no row exists.

## Legacy Google Forms

`CONTRACT_GOOGLE_FORM_LINK` is used only by the superseded SPEC-09 compatibility UI/API and is not displayed by the live application. The application does not call the Google Forms API, read responses from that form, or synchronize the Form with the in-app schema. Only `POST /api/contracts/submit` appends a contract row.

## Make

The backend sends a JSON webhook payload to the Make webhook URL configured in `MAKE_WEBHOOK_URL`.

- Payload mapping is implemented in `backend/src/mappers/makePayloadMapper.ts`.
- The webhook receives full submission metadata, folder information, agent data, and media details.

## Property Google auth modes

### User OAuth2 (recommended)

- Configure `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_REFRESH_TOKEN`.
- Uploads run under the authenticated user account and use that user's Drive quota.

### Service Account fallback

- Configure `GOOGLE_SERVICE_ACCOUNT_KEY_JSON`.
- Share the target sheet and parent Drive folder with the service account email.
- Optionally configure `GOOGLE_SUBJECT_EMAIL` for domain-wide delegation if needed.

## Legacy contract Google auth

For Contract Generation, the service account is required rather than a fallback. Share only the configured destination spreadsheet with that principal and grant the minimum role required to read row 1 and append values (`Editor` on that spreadsheet). Contract submission does not require general Drive access or ownership of unrelated spreadsheets. Keep service-account JSON server-side and rotate credentials according to the deployment's secret-management policy.

## Supabase administrator authentication

SPEC-19 uses Supabase Auth for email/password registration and login, with Google OAuth retained as an alternate login through the browser's public Supabase client. The backend uses the server-only `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to create confirmed password accounts and validate Google access tokens. Registration and the Google session handoff record the account in `public.contract_admin_users` with administrator access. The browser receives the application's signed HttpOnly session cookie; the service-role key is never sent to the browser.
